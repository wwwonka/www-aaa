## Revue de code — 3 bugs trouvés, tous corrigés + verrouillés par golden test

1. **`src/sim/GameSim.ts` (reversal wave)** — `reversal.advance(dtSec)` tournait juste après
   `trigger()`, AVANT que `steering.compute()` ne lise `waveActive` pour ce même step. Pour un banc
   compact (rayon petit / `REVERSAL_WAVE_SPEED` élevée), l'onde pouvait se terminer dans le
   `advance()` du step même où elle avait été déclenchée → `waveActive` déjà `false` quand
   `compute()` s'exécutait → l'effet fouet ne s'appliquait jamais pour ce déclenchement,
   silencieusement. **Fix** : `reversal.advance(dtSec)` déplacé en fin de `stepOnce()`, après
   `steering.compute()` (et `physics.step()`) — l'onde est désormais garantie observable par le
   steering au moins un step complet avant de pouvoir s'éteindre.
   **Golden test** : `tests/unit/sim/ReversalWave.test.ts` — 2 nouveaux cas : (a) `waveActive` est
   `true` immédiatement après `trigger()`, avant tout `advance()`, même avec des délais tous à 0 ;
   (b) un banc assez compact (rayon ~0.01) s'éteint bien en un seul `advance(SIM_STEP_MS/1000)`
   réel — documente noir sur blanc le scénario qui rendait l'ordre non négociable.

2. **`src/core/assets/AssetsManager.ts` (`criticalReady`)** — dans `warmUp()`,
   `pendingSet.delete(entry.path)` s'exécutait inconditionnellement après le try/catch, y compris
   sur le chemin d'erreur. Un asset critique (police) qui échouait au fetch (offline, CDN) était
   quand même retiré du pending set → `criticalReady` se résolvait comme si tout était chargé → la
   garantie documentée (« await avant le premier rendu de texte pour éviter le flash ») était
   silencieusement rompue. **Fix** : le `delete` est descendu dans le bloc `try`, juste après le
   `completed++`/`onEvent('progress')` — un chemin d'erreur ne retire plus jamais un asset critique
   du pending set ; une prochaine tentative de `warmUp()` (retry / namespace suivant) peut encore le
   faire réussir et résoudre `criticalReady`.
   **Golden test** : `tests/unit/core/assets/AssetsManager.test.ts` (nouveau fichier) — mock
   `fetch` + `assetDb` : (a) `criticalReady` reste EN ATTENTE après un échec de fetch critique ;
   (b) elle finit par se résoudre une fois qu'un `warmUp()` ultérieur réussit sur ce même asset.

3. **`src/input/signaling/PairingChannel.ts` (`sendStart`)** — appelait `start.send(null)` SANS
   `{ target: peerId }`, contrairement à tous les autres envois du fichier (`connect`, `paired`,
   `busy`, `hoReq`, `hoState`, `hoAck`). Diffusait `start` à toute la room au lieu du seul peer pairé
   — contredisait son propre commentaire d'interface. Masqué jusqu'ici par la garde
   `peerId === pairedPeerId()` dans `pairingHost.ts` (un fichier plus loin), pas par le canal
   lui-même. **Fix** : `sendStart` prend maintenant un `peerId` explicite (signature alignée sur
   `sendHandoffRequest`/`State`/`Ack`) et cible `{ target: peerId }` ; `pairingHost.notifyLocalPlay`
   résout `pairedPeerId()` et no-op si `null`, même pattern que les autres envois de handoff.
   **Golden test** : `tests/unit/input/signaling/PairingChannel.test.ts` (nouveau fichier) — mock
   `@trystero-p2p/nostr` : (a) `sendStart(peerId)` envoie `{ target: peerId }`, comme `hoReq` ; (b)
   n'appelle plus jamais `send` sans options (la forme exacte du bug).
